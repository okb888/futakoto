# ふたこと コードレビュー（マルチエージェント方式）

専門家エージェントが並列でコードを読み、最後に1人が統合判定する。

---

## 実行方法

Claude Code を起動して、以下の「司令プロンプト」をそのまま貼る。

```
下記の8つのエージェントタスクを並列で実行してください（Agent toolを8つ同時に呼び出す）。
各エージェントの結果が揃ったら、最後に「統合レポート」を出力してください。

プロジェクトパス: /Users/okabehiroyuki/futakoto/
```

## Agent 1 — セキュリティエンジニア

```
あなたはセキュリティ専門のエンジニアです。
「ふたこと」アプリのコードを**攻撃者の目線**でレビューしてください。

## 読むファイル（順番に全文読む）
1. `firestore.rules`
2. `functions/src/shared.ts`（consumeAiQuota / isPremiumUser を重点的に）
3. `functions/src/revenuecat-webhook.ts`（全文）
4. `lib/auth-providers.ts`
5. `lib/purchases.ts`

## チェック項目（必ず全て確認）

### Firestore ルール
- [ ] 認証なしで読める collection はないか
- [ ] ユーザーAがユーザーBのデータを書き換えられないか
- [ ] `premium` / `aiCreditsUsed` / `partnerUid` をクライアントから直接書けないか（allow update の hasOnly を確認）
- [ ] パートナーとして登録されていない第三者が `entries` を読めないか
- [ ] `inviteCodes` の read が認証済み全員に開いているリスクはあるか（UID照合に使われるが列挙攻撃は可能か）

### Cloud Functions 認証
- [ ] 全 httpsCallable 関数で `request.auth` の null チェックがあるか
- [ ] `uid` をクライアントから受け取っている箇所で `request.auth.uid` との一致確認をしているか（なりすまし防止）

### 課金・権限昇格
- [ ] RevenueCat Webhook で `premium=true` を書く前に、Webhook 認証（`REVENUECAT_WEBHOOK_AUTH`）が検証されているか
- [ ] `isPremiumUser()` のロジックで、削除済みユーザーの `partnerUid` が残ったままになった場合に他人が Premium になれないか
- [ ] クライアントから `premium` フラグを直接 `updateDoc` できないか（firestore.rules の update 制限を確認）

### シークレット・情報漏洩
- [ ] `console.log` に uid 以外のユーザーデータが出力されていないか
- [ ] エラーレスポンスに内部情報（スタックトレース・DB パス等）が含まれていないか

### プロンプトインジェクション
- [ ] `wrapUserData()` が全ての AI 呼び出し箇所で使われているか（`ai-functions.ts` と照合）
- [ ] `DATA_HANDLING_INSTRUCTION` がプロンプトの先頭側に配置されているか

## 出力フォーマット
各問題を以下の形式で出力:
```
🔴/🟡/🟢 [ファイル名:行番号] 問題タイトル
- 問題: （何が起きているか）
- 攻撃シナリオ: （悪用されるとどうなるか）
- 修正: （具体的な変更内容）
```
最後に「セキュリティ問題 合計: 🔴N件 🟡N件 🟢N件」を出力。
```

## Agent 6 — UX・ユーザビリティ専門家

```
あなたはモバイルアプリのUXリサーチャーです。

## 評価の基準：ニールセンの10ヒューリスティクス
1. システム状態の可視性（今何が起きているか常に分かるか）
2. 現実世界との対応（専門用語・難しい言葉を使っていないか）

4. 一貫性と標準（iOS の標準動作から外れていないか）
5. エラー防止（危険な操作の前に確認があるか）
6. 記憶負荷の最小化（何をすべきか迷わないか）
7. 柔軟性と効率（慣れたユーザーは素早く操作できるか）
8. 美的・最小限のデザイン（余分な情報・装飾がないか）
9. エラーからの回復（エラーメッセージが何をすればいいか教えているか）
10. ヘルプとドキュメント（機能の使い方が自明か）

## 読むファイル
1. `app/(app)/index.tsx`（ホーム画面）
2. `app/(app)/post.tsx`（投稿画面）
3. `app/(app)/consult.tsx`（AI相談画面）
4. `app/login.tsx`（ログイン・初回体験）

## チェック項目

### 初回体験・オンボーディング
- [ ] ログイン直後に「何をするアプリか」すぐわかるか（ペアリング前の空状態がわかりやすいか）

- [ ] パートナーがまだ参加していない状態で「相手の投稿がない」ことが不安でなく説明されているか

### ホーム画面
- [ ] 今日記録がない状態の「空状態」デザインがあるか（何もないと離脱につながる）
- [ ] 自分とパートナーの投稿が「どちらがどちら」か一瞥でわかるか
- [ ] 連続記録（ストリーク）表示がモチベーションになるか・プレッシャーにならないか

### 投稿フロー
- [ ] 気分絵文字 → テキスト入力 → 投稿 のステップ数は最短か（1画面内で完結しているか）
- [ ] 「自分だけ」「パートナーにも見せる」の切り替えが分かりやすいか（特にデフォルト値が正しいか）
- [ ] 投稿完了後のフィードバックがあるか（成功した感じが伝わるか）

### AI相談フロー
- [ ] AI同意モーダルが「怖い・難しい」ではなく「安心できる」トーンか
- [ ] AIの返答を読んだあと「次に何をすればいいか」が明確か

### 課金・ペイウォール
- [ ] 無料枠を使い切ったときのメッセージが「ブロックされた感」でなく「もっと使いたい気持ち」に寄り添っているか
- [ ] ¥500/月の価値が一言で伝わるコピーがあるか
- [ ] 「いつでも解約できる」という安心感が提示されているか

### エラー・空状態
- [ ] ネットワークエラー時のメッセージが「何をすれば復帰できるか」を教えているか（「エラーが発生しました」だけはNG）
- [ ] AI呼び出し失敗時に「もう一度試す」ボタンがあるか

### 感情的満足度（夫婦アプリ固有）
- [ ] アプリ全体のトーン（文言・色・フォント）が「親密さ」「温かさ」を感じさせるか
- [ ] パートナーの投稿が届いたとき「嬉しい」と感じる演出があるか
- [ ] AI機能が「道具っぽい」ではなく「寄り添っている」感じがあるか
```
