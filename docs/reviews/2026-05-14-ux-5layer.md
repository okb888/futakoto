## Layer 1: Strategy（戦略）

### ユーザーニーズ

| ニーズ | 充足度 |
|--------|--------|
| 言いたいけど言えないモヤモヤを届けたい | ✅ コア機能で解決 |
| 返信・既読プレッシャーなし | ✅ 返信機能を意図的に不採用 |
| 相手の気持ちを「解釈してほしい」 | ✅ aiInterpretで対応 |
| 自分の気持ちを整理したい | ✅ aiConsult（壁打ち） |

### プロダクトゴール

| 目標 | 状況 |
|------|------|
| 2026-08-31 に月額¥500 課金1件 | TestFlight 提出済み、審査5/31予定 |
| AI活用でリリース経験を積む | ほぼ達成（課金・AI・認証完備） |

### 戦略上のリスク

- **集客がボトルネック**: SNS 未着手、LP 仮公開のまま。課金転換より「見つけてもらう」が先の課題

- **作者自身が夫婦関係の当事者**: ユーザーインサイトは深いが、感情的距離の管理が難しい局面

## Layer 2: Scope（スコープ）

### 実装済み機能（充実度は高い）

```
認証       Email / Google / Apple Sign-in
ペアリング  6桁招待コード・pairedWith連携
投稿       気分5段階 + テキスト + 公開/非公開切替 + 削除
AI 6種     aiRewrite / aiConsult / aiDraftOptions
           aiDraft / aiInterpret / aiSummary
振り返り   カレンダー気分ヒートマップ（自分=背景、相手=ストリップ）
相談       チャット履歴・お気に入り・投稿転記
課金       RevenueCat / 月5回無料 / 月額¥500・1契約2人
```

### スコープの意図的な非採用（良い判断）

- **返信機能なし** → チャット化を防ぎ「発信のみ」の安全性を確保
- **お気に入りは相手に非通知** → プレッシャーゼロ設計
- **広告なし** → 体験の純粋性を保つ

### スコープの未充足

| 項目 | 状況 | 影響 |
|------|------|------|
| LP 本番版 | 仮公開中 | 集客力が弱い |
| SNS 運用 | 完全未着手 | 流入ゼロリスク |
| Apple Small Business Program | 未登録 | 手取りが 30%（¥350）のまま |
| プライバシーポリシー | URL 未有効 | App Store 審査リスク |

## Layer 3: Structure（構造）

### 情報アーキテクチャ

```
ふたこと
├── ホーム        ← ペア双方の投稿タイムライン
├── 投稿          ← 気分 + テキスト + 公開設定
├── 相談          ← AI壁打ちチャット + 履歴 + お気に入り
├── カレンダー    ← 気分ヒートマップ + AI月次要約（予定）
└── お気に入り    ← 自分だけの印 + 設定（同居）
```

### 主要フローの評価

| フロー | 評価 |
|--------|------|
| ログイン → ペアリング（招待コード）| 6桁コードはシンプルで良い |
| 投稿：絵文字選択 → テキスト → 送信 | 最短3タップで完結、摩擦が少ない |
| AI相談：入力 → 応答 → 継続/お気に入り | 会話継続性あり、良設計 |
| ペイウォール：5回消費 → モーダル → 購入 | 5タイミングの誘導設計は丁寧 |

### 構造上の問題

1. **「お気に入り」タブに設定が同居**: タブの意味が2つになり認知コストが生じている
2. **オンボーディングフロー**: 「招待コードを相手に渡す→インストール→ペアリング」の流れを案内する UI が弱い可能性。β配布で要確認
3. **タブ5つは上限**: Apple HIG は 5 タブが最大。今後機能追加時に IA が破綻するリスク

## β配布前に確認すべきこと

1. **オンボーディングUX**: 招待コードをパートナーに渡す→インストール→ペアリング完了の流れを実機で通す
2. **borderSoft/background の差**: カード境界の視認性が実機でどう見えるか確認

## 長期積み残し

- 設定画面のサブページ分割（5グループ化）
- お気に入りタブと設定の分離
- カード背景をグラデーション or 微細テクスチャ検討（G. 長期対応）
