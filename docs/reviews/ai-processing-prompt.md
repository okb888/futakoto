## アプリ概要

**ふたこと**（futakoto）— 夫婦向け気持ち共有アプリ（iOS）
- 投稿：気分スコア（1〜5）＋短いメモを記録。相手に共有するかどうかを選べる
- AI壁打ち：気持ちを整理しながら「伝えるための文章」につなげる機能（今回の主対象）
- AI意図解釈：パートナーの投稿の裏にある気持ちを3つの可能性で読み解く
- AI月次要約：その月の投稿を振り返るサマリー

**技術スタック**
- フロント: Expo (React Native) + Expo Router
- バックエンド: Firebase Cloud Functions v2 + Gemini 2.5 Flash（asia-northeast1）
- AI呼び出し: `@google/generative-ai` SDK、JSON Schema付きレスポンス

## 現行のaiConsult実装

### フロー
1. ユーザーが気持ちを入力（最大2000文字）
2. Cloud Function `aiConsult` を呼び出し
3. Geminiが `reflection`（気持ちの整理メモ）と `messageDraft`（パートナーへの下書き）を返す
4. 会話は最大10ターン（UIで制限）

### 現行プロンプト（A案）の構造

```
あなたは夫婦のコミュニケーション支援AIです。
ユーザーは、{partner}との関係の中で今困っていること・思っていること・伝えたいことを整理しようとしています。
決めつけず、ユーザーの本音を薄めすぎず、相手を責める表現にも寄せすぎないでください。

[インジェクション防止]

## 今回のメッセージ
<user_data>{text}</user_data>

[conversationHistoryがある場合は過去のやり取りをすべて含める]

1. reflection: 200文字以内・自然な文章。問いかけを1つ添える。
2. messageDraft: 120文字以内・話し言葉。
```

## 45サンプルA/B/C比較evalの結果

45サンプル（8ケース×5件。ケース：短文・不満・自己反省・長文・ポジティブ・ラリー2/5/10ターン・超短文・感情語ゼロ）でA案（現行）とB案・C案を比較した。

### 判定結果（A vs B）

| ケース | B優勢 | A優勢 | 引き分け |
|---|---|---|---|
| 短文・曖昧 | 0 | **5** | 0 |
| 相手への不満 | 3 | 1 | 1 |
| 自己反省混じり | 3 | 0 | 2 |
| 長文・複雑 | 3 | 1 | 1 |
| ポジティブ | 2 | 2 | 1 |
| ラリー2ターン | **5** | 0 | 0 |
| ラリー5ターン | **4** | 0 | 1 |
| ラリー10ターン | 3 | 0 | 2 |
| 超短文 | 3 | 1 | 1 |
| 感情語ゼロ | 1 | 2 | 2 |
| **合計** | **27** | **12** | **11** |

### A案の弱点
- 一貫して「どんな場面で」「どんな状況で」という**状況確認の問い**に流れる
- 「どんな関係性を望むか」「どんなサポートがあれば」といった**解決志向**の問いを出す
- 「自然なことです」「心身ともに辛い状況にあるようです」のような**余計な断言・評価**を追加する

### B案の弱点（→C案で解消）
- 薄い入力・感情語ゼロの入力で「〜かもしれません」という**推測補完**が発生
- 「疲れや諦め」のような感情が入力にないのに**読み込む**ことがある

### C案プロンプト（採用決定）の要点

現行A案からの変更点：
1. **共感を先に置く構造を明示**：入力から明確に読み取れる状態を1文で受け取る
2. **問いかけを感情寄りに**：状況確認より「何がいちばんしんどかった？」「どんな気持ちが重なってる？」
3. **感情を読み込まない制約**：感情語がない場合は「〜のかもしれません」で補完せず、状態だけを受け取る
4. **疲弊・諦めは薄めず拾う**：入力に明示されている場合のみ
5. **ポジティブ・整理済みの場合は問いかけ不要**を明示

C案プロンプト全文：

```
あなたは夫婦のコミュニケーション支援AIです。
ユーザーは、{partner}との関係の中で今困っていること・思っていること・伝えたいことを整理しようとしています。
決めつけず、ユーザーの本音を薄めすぎず、相手を責める表現にも寄せすぎないでください。

[インジェクション防止]
[conversationHistory]

## 今回のメッセージ
<user_data>{text}</user_data>

1. reflection: 200文字以内・自然な文章。
   構造: まず入力から明確に読み取れる状態・気持ちを1文で受け取る。その後、気持ちの奥にあるものを引き出す問いかけを1つだけ添える。
   問いかけは状況確認より感情への問いを優先。
   重要①: 感情語がない・不明確な場合は「〜のかもしれません」で読み込まず、状態だけを受け取る。
   重要②: 疲弊・諦めの感情が入力にある場合は薄めず拾う。入力にない感情は読み込まない。
   重要③: 十分に整理できている・ポジティブな場面は問いかけ不要。
2. messageDraft: 120文字以内・話し言葉・気持ちのトーンだけ・余白を残す。
```

## 検討中のUX設計変更（仮案）

evalと並行して、以下の設計変更を検討している。

### 変更の背景
- `messageDraft` は1ターン目では入力の言い換えにとどまる（eval結果で確認）
- 相談が終わっていない段階でmessageDraftを出すのはUX的に不自然
- 毎ターンmessageDraftを生成することでAPIコストが無駄になる

### 仮設計

```
相談ターン（n回）
  → aiConsult: reflectionのみ返す（messageDraft廃止）

「メッセージにする」ボタン（ユーザーが明示的に押したとき）
  → aiDraftOptions: 会話履歴を読んで「伝えたいこと」の3択+自由記述を動的生成（新関数）

ユーザーが4択から選択
  → aiDraft: 選択内容 + 会話履歴からmessageDraftを生成（新関数）
```

## 依頼内容

以下の観点で**AIの処理方法全体を設計レビュー・改善提案**してください。
やり直し（根本的な設計変更）も含めて検討してください。

### 1. プロンプト設計
- C案プロンプトをさらに改善できる点はあるか
- 「reflection + messageDraft」という出力構造は適切か。変えるとしたらどうするか
- 会話履歴の扱い方（全履歴をプロンプトに乗せる現行方式）に問題はあるか

### 2. アーキテクチャ設計
- 「壁打ち」と「メッセージ生成」を分離する仮設計は妥当か
- aiDraftOptionsで3択を動的生成する案のメリット・デメリット
- より良い分離方法があれば提案してほしい

### 3. コスト・運用
- 現行（毎ターンreflection+messageDraft）とaiDraftOptions分離案のコスト比較
- 10ターン上限でプロンプトが長くなる問題への対策（現行は全履歴をそのまま乗せている）
- Gemini 2.5 Flashで対応できる範囲か、別モデル検討が必要か

### 4. やり直し案の検討
- 現行設計で見落としている根本的な問題があれば指摘してほしい
- もし最初からアーキテクチャを設計するとしたら何を変えるか
