### V3-CRIT-1. `app/(app)/index.tsx:210` `ArrowRight` 未importでクラッシュ

[index.tsx:13](../app/(app)/index.tsx#L13) で import しているのは `{ Plus, Heart, Sparkle, Star }` のみ。にもかかわらず [index.tsx:210](../app/(app)/index.tsx#L210) で `<ArrowRight size={13} ... />` を使用。

```diff
- import { Plus, Heart, Sparkle, Star } from 'phosphor-react-native';
+ import { Plus, Heart, Sparkle, Star, ArrowRight } from 'phosphor-react-native';
```

**最優先**。

### V3-CRIT-2. `invalidateInterpretationCacheOnEntryUpdate` が全ユーザー走査

[functions/src/index.ts:835](../functions/src/index.ts#L835) で `db.collection('users').get()` → 全ドキュメントに対して `delete` を発行している。

- 解釈キャッシュを持つのは「投稿者のパートナー」だけ
- 修正：投稿者の `partnerUid` を 1 回取得し、そのユーザーの cache 1件を delete すれば十分
- 数千ユーザー規模で Firestore 読み取り無料枠を瞬時に食う

```typescript
// 修正案
const authorSnap = await db.doc(`users/${uid}`).get();
const partnerUid = authorSnap.data()?.partnerUid;
if (!partnerUid) return;
await db.doc(`users/${partnerUid}/interpretationCache/${cacheKey}`).delete().catch(() => {});
```

### V3-CRIT-3. `aiInterpret` のキャッシュキー検証なし

[functions/src/index.ts:674](../functions/src/index.ts#L674) で `cacheKey = entryOwnerId_entryId` を viewer 側 cache に保存しているが、`entryOwnerId` がクライアント任せ。

- 自分の cache に書くだけなので情報漏れはなし
- が、悪意ある viewer が任意 entryOwnerId を渡してキャッシュ汚染可能
- **より深刻**：パートナー以外の任意の投稿で AI を呼び出してコストを乱用できる
- 対策：サーバー側で `users/{entryOwnerId}/entries/{entryId}` を `get()` し、本人 or 自分の partnerUid の投稿であることを確認してから AI を回す

### V3-CRIT-4. `aiConsult` `conversationHistory` がクライアント任せ

[functions/src/index.ts:598](../functions/src/index.ts#L598) で受け取った会話履歴をプロンプトに混ぜている。

- MAX_TURNS=10 のクライアント上限がサーバー側にない（直接 callable を叩けば無限）
- 任意の履歴を捏造して AI を誘導できる

`sessionId` を必須にし、サーバー側で Firestore からセッションを引いて長さ・本人性を検証する形に切り替える。

## 1. 機能設計レビュー

### 強み
- **「気持ちの整理」→「相手に伝える文の生成」の分業**が明快。壁打ち（紫＝AI）／パートナーへの文（緑＝ふたり）の色分けは秀逸
- **投稿元の壁打ちセッション（`sourceConsultationSessionId`）を辿れる動線**は夫婦アプリとしての差別化
- 月次AI要約の自分／パートナー切替、解釈キャッシュ、AI課金の月次・日次クォータ、メール認証、エクスポートと、リリースに必要なパーツがほぼ揃っている

### 抜け・気になる設計

#### V3-FN-1. `aiConsult` の messageDraft を毎ターン生成している
v2 の検討メモにある通り。早期に「reflectionのみ→明示的にメッセージ化」へ移行を。**毎ターンdraftは UX 的にも整理を急かすノイズ**。

#### V3-FN-2. 新しい壁打ちを始める時の確認がない
[consult.tsx:129 `handleStartNewConversation`](../app/(app)/consult.tsx#L129) は無確認で `setConversation([])`。お気に入り未保存の会話を 1 タップで失う。`handleResumeSession` は確認しているのに非対称。

#### V3-FN-3. 投稿削除時のクリーンアップ漏れ
`deleteEntry` を呼んだあと、自分側 `favorites` と相手側 `interpretationCache` の該当 entry が孤児化する。`onDocumentDeleted` トリガーで掃除するのが安全。

#### V3-FN-4. 共有範囲のデフォルト `shared`
プライバシー的には初期値 `private` の方が安全側だが、夫婦間の体験設計としては `shared` が正解の可能性も。少なくとも「直前に選んだ可視性を覚える」だけでも誤共有リスクは下がる。

#### V3-FN-5. ペア解除後の相手側からのデータ可視性
解除した瞬間に相手は過去の shared 投稿が読めなくなる。これが想定通りなのか、明示UI（「解除すると相手は過去の共有投稿を見られなくなります」）でユーザーに伝える必要あり。

#### V3-FN-6. MAX_TURNS=10 の意味
クライアント側だけで止めても無意味（直接 callable を叩かれたら抜ける）。サーバー側にも検証を。

## 2. UX

### 摩擦ポイント

#### V3-UX-1. AIで整える後、元に戻す導線は1段だけ
`previousMemo` は1スタックなので、2回置換すると最初の文章には戻れない。AI試行錯誤の流れではここが効く。

#### V3-UX-2. post.tsx の日付ピッカーが開閉トグル制で時刻ピッカーはモーダル
混在しているので意図的でないなら統一。日付もモーダルに揃えると一貫する。

#### V3-UX-3. calendar フィルタ「相談」のときも自分／相手切替ボタンが見えている
`filter === 'consultation'` のときは自分／相手切替を隠す or 無効化が自然。

#### V3-UX-4. 解釈キャッシュの「再度試せる」導線がない
パートナーの投稿に対する `aiInterpret` 結果は永続化されるが、UI 上「いつ解釈したか」「再度試せるか」が分からない。古くなった解釈に閉じ込められる。「もう一度読み解く」ボタン。

#### V3-UX-5. 空状態のCTAが弱い
ペア未連携時のホーム上部「設定タブからパートナーと繋がろう」だけでは導線が遠い。タップで設定へ飛ばすか、招待コードを直接表示するくらいでも良い。

### 良い摩擦削減
- 投稿の「今日／昨日／一昨日」クイック設定
- `hitSlop` の付与
- `KeyboardAvoidingView`
- `useFocusEffect` でのキャンセラブルロード — どれも丁寧

## 4. コード品質

### V3-CQ-1. 重複・抽出余地
- `formatDate` `formatTime` `dateKey` `sortMillis` が calendar/index/consult/post に分散。`lib/format.ts` 集約
- `partnerName` 算出（`partnerProfile?.displayName ?? partnerProfile?.email?.split('@')[0] ?? 'パートナー'`）が4箇所以上。`lib/profile.ts` 集約（v2 P1-6 で起票済）
- ホーム / カレンダーで Entry の操作系（toggleFavorite / handleEdit / handleToggleVisibility / handleDelete / actionKey）がほぼ同一実装。`useEntryActions(uid, onChange)` カスタムフック化を

### V3-CQ-2. バグの種
- `calendar.tsx:79` `latestByDate` は同日複数の最新を取りたいだけだが、`>=` で更新するため、同 `seconds` のときに後勝ちが期待外れになる。`>` に
- `calendar.tsx:281, 288` `sortSeconds: entry.createdAt?.seconds ?? 0` で秒粒度ソート。同分内の前後がぶれる。`sortMillis(entry.createdAt)` を使う
- `db.ts:191` `getRecentEntries` が `limit(50)` 固定で、ホームではこれを起点にパートナー shared と混合ソート。**自分の投稿が50件中の50件目にいる時、相手の最新が混ざるとリストから自分が押し出されて見える**。少なくともホームでは「自分N件 + 相手N件 → 直近K件」のようにK件で揃える方が体験が安定
- `post.tsx:175` `applyRecordDate` で未来は現在に戻すが、ユーザーには黙って書き換える挙動。日付選択UIで未来日を `maxDate` で隠している（OK）が、Quick Date のロジックでも保険として残す形は親切

### V3-CQ-3. 型 / API
- `Entry.createdAt: any` は痛み。Firestore Timestamp 用の専用型 or `Timestamp | { seconds: number; nanoseconds: number }` のユニオンに。`toDate()` の存在チェックが各所に散らばる原因
- `db.ts:303 toggleFavoriteEntry` の `isFavorite` 引数は「現在お気に入り済みか」を渡す呼び出し規約。意図が逆に読めるので `currentlyFavorite` などに改名する価値あり

### V3-CQ-4. Functions 側
- `getAiClient` のキー復号で `GEMINI_API_KEY=...` プレフィックスや引用符を剥がしているのが気になる。secret に余計な装飾が混入しているなら secret 側を直すべきで、コードでガードするのは意図がぼやける
- `aiConsult` の `conversationHistory` を文字列結合プロンプト化している都合、`<user_data>` タグをユーザーが本文に書いた場合のエスケープなし。プロンプトインジェクション耐性は Gemini の素の堅牢さに依存。少なくとも「`</user_data>` が本文に含まれていたら置換」する1行は入れたい

### V3-CQ-5. パフォーマンス
- ホームの `load` がフォーカスごとに 4〜6 並列クエリ。`useFocusEffect` のキャンセル処理は入っているが、頻繁にフォーカスが切り替わる遷移で重なりやすい。せめて 30秒以内の再フォーカスは前回結果を表示しつつ background fetch する `staleWhileRevalidate` を
- カレンダーが月切替のたびに自分のエントリだけキャッシュし、相手の500件は毎回再取得。ホームと同じく軽いキャッシュを `partnerEntries` にも
