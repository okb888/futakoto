## 1. なぜ再設計が必要だったか

A→B→C→D の進化を振り返ると、**毎回「失敗ケースを潰すルール」を足した結果**になっていた。

- D案（現行本番）はルール7〜9箇条 + 固定問いかけ型3パターン + few-shot（良い/悪い対比）
- 問いかけが機械的で「続けて話したい」気持ちを削ぐ
- 「reflection 生成タスク」発想になり、自然な対話の温度感を失っている
- トップダウンの設計が一度もされていなかった

---

## 2. E案 設計原則

### 原則1: ルールではなく「人格」で制約する
ルール7個より、キャラを1つ強く持たせる方が LLM は安定する。

### 原則2: 「悪い例」を出さない
few-shot は「良い例だけ複数」。悪い例を示すと LLM が過剰に慎重になり必要な共感まで削る（contrastive bias）。

### 原則3: 問いかけは「方向」のみ示す
具体的な問いの型を固定しない。「気持ちの奥にあるもの・まだ言葉になっていないものを引き出す方向」のような抽象的方向性だけ指示し、実際の文はLLMがその場で生成する。

### 原則4: 「reflection 生成」をやめて「返事」に
出力フィールド名: `reflection` → `reply`（ユーザーへの返事として生成する発想に変える）

### 原則5: 1タスクに絞る
`readyForDraft` はaiConsultから外す。ユーザーが「メッセージにする」ボタンを能動的に押す設計に変更（UX的に正直）。

## 3. 3キャラ設計（確定）

| キーワード | UI説明（スラッシュ以降） | 人格・特性 |
|---|---|---|
| **ソフト** | そっと聞く・問いかけは必要なときだけ | 静かに受け止める。推測せず、ラベルを貼らない。問いかけは最小限。やわらかい敬語。淡い温度感 |
| **フレンドリー** | タメ口で、気の置けない友人のように | タメ口・フランク・対等。「うん」「わかる」「それしんどいよね」の同じ目線。ストレートに問いかける |
| **ロジカル** | 感情と事実を分けて、状況を構造化する | 「起きていること」「こたえていること」「方向性」を分けて返す。感情への共感より、状況の見取り図を作る。男性ロジカルタイプに刺さる |

### 3キャラのサンプル返答（入力: 「皿洗いしてくれない、毎回言わないとやらない」）

**ソフト**:
> 毎回言わないと動いてくれない、そのことがしんどいんですね。一番ひっかかっているのは、皿洗いそのもの？それとも別のところですか？

**フレンドリー**:
> それ、毎回言わないと動かないのほんとしんどいよね。でもさ、一番モヤってるのって皿洗いのことなのかな？それとも他にひっかかってることがある？

**ロジカル**:
> 起きていることは「皿洗いを毎回お願いしている」状態。こたえているのは、皿洗いそのものより「言わないと気づかれない」ことに見えます。気づいてもらえなさが本題かどうか、整理してみますか。

## 4. communicationStyle の分離（確定）

| 設定 | 用途 | 反映先 |
|---|---|---|
| `aiPersona` (新規) | 壁打ちAIの話し方（ソフト/フレンドリー/ロジカル） | `aiConsult` のみ |
| `communicationStyle` (既存) | パートナーへの伝え方・文案の文体 | `aiDraft` のみ |

**現行の問題**: `communicationStyle` が `aiConsult` と `aiDraft` 両方に注入されていた。設定UIの説明文「AIが文案を作るときの文体」とも乖離。→ `aiConsult` から `communicationStyle` を外す。

## 7. プロンプト実装方針

### 共通骨格（3キャラ共通・変わらない部分）

```
大事にしてほしいこと（共通ルール）:
- ユーザーが書いた言葉とトーンに寄り添う。書いていない気持ちを推測・ラベル付けしない
- 「もう疲れた」「もう限界」「諦めてる」のように明示された言葉は薄めずそのまま受け取る
- 気持ちの奥にまだ言葉になっていないものが見えるときは、その方向に短い問いをひとつだけ添える
- 問いはユーザーの言葉に寄り添う形で、その場で生み出す（固定フレーズを使わない）
- 整理がついている・ポジティブな話が落ち着いて伝わってきたときは問いを添えない
- 200文字以内・自然な話し言葉
```

### キャラ別差分（ペルソナ部分のみ入れ替え）

```ts
const PERSONA_PROMPTS = {
  soft: {
    role: 'やわらかく、静かに話を聞く相手',
    tone: 'やわらかい敬語。淡く、急かさず、判断しない。',
    // few-shot: 良い例 × 5件（short/positive/complaint/exhausted/rally）
  },
  friendly: {
    role: '気の置けない友人',
    tone: 'タメ口・フランク。「うん」「わかる」のように同じ目線で。',
    // few-shot: B版トーンの良い例 × 5件
  },
  logical: {
    role: '状況を構造化する冷静な相手',
    tone: '「起きていること」「こたえていること」「方向性」を分けて返す落ち着いた敬語。',
    // few-shot: 構造化返答の良い例 × 5件
  }
};
```

### 出力フォーマット（3キャラ共通）

```json
{
  "reply": "..."
}
```

`reflection` → `reply` へのリネームに伴い、[consult.tsx](/Users/okabehiroyuki/futakoto/app/(app)/consult.tsx) の表示変数名も変更が必要。

## 8. evalプラン

### 既存45サンプルを3キャラ × judge.ts で評価

```bash
cd futakoto/eval

# E案 3キャラを全45サンプルで実行
npx tsx run.ts E-soft    # 全ケース
npx tsx run.ts E-friendly
npx tsx run.ts E-logical

# judge.ts で自動採点（3軸rubric）
npx tsx judge.ts results/E-soft_all.json
npx tsx judge.ts results/E-friendly_all.json
npx tsx judge.ts results/E-logical_all.json
```

### 評価観点の追加（既存3軸 + キャラ一貫性）

| 指標 | ソフト | フレンドリー | ロジカル |
|---|---|---|---|
| 受容の精度（0-3） | 3.0付近 | 3.0付近 | 3.0付近 |
| 問いかけの質（0-3） | 2.0以上 | 2.0以上 | 2.0以上（問い不要な場合もある） |
| 自然さ（0-3） | 2.5以上 | 2.5以上 | 2.5以上 |
| **キャラ一貫性** | 敬語率95%以上 | タメ口率95%以上 | 構造化返答率70%以上 |

### 合格ライン（E案採用の判断基準）

- **各キャラの avgTotal ≥ 7.0 / 9**
- **D案（現行本番）との比較で各キャラが同等以上**
- キャラ一貫性チェックをパス
